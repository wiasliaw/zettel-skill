# 設計理念

本文說明 zk plugin 各項行為背後「為什麼要這樣設計」——不只是 plugin 做了什麼，而是為什麼採用這種做法。閱讀前建議先熟悉六個指令（`init`、`fleeting`、`literature`、`permanent`、`query`、`adapt`）與三個 subagent（`zk-research`、`zk-atomizer`、`zk-adversarial-review`）；若還不熟悉，建議先看教學文件。

## 1. 兩層筆記模型

**理念。** 每篇筆記恰屬兩層之一。**暫存層（staging）** 是尚未定稿的草稿：閃念筆記（fleeting）與文獻筆記（literature），扁平存放（不分 topic 子目錄）、不進語意檢索索引、也絕不是任何 wikilink 的連結對象。**歸檔層（filed）** 是成品：永久筆記（permanent，即原子筆記／atomic note）與 reference 筆記，依 topic 分區存放、進索引、可自由被連結。兩層之間唯一的轉換方向是歸檔——暫存層筆記經拆分後歸入歸檔層，沒有回頭路。

**為什麼。** 一個還沒想清楚的念頭、一份還沒讀完的來源，不該出現在檢索結果裡，也不該累積被連結的次數。歸檔層的筆記本質上是可被引用的——一旦某篇筆記可被連結，其他筆記就開始依賴它的措辭。讓暫存層扁平且不進索引，等於防止半成品悄悄變成整個卡片盒（slip-box）依賴的基礎設施。

**落在哪些行為。** 閃念筆記與文獻筆記兩個工作流程只寫入各自的暫存位置；permanent 是唯一寫入歸檔層的指令，且只讀暫存層作為輸入。目錄名稱本身並非固定——每一階段的存放位置都是初始化訪談時由使用者決定、config 可自訂的值——但兩層邊界與單向轉換不可自訂。

## 2. 原子筆記與主張式標題

**理念。** 一篇永久筆記是原子的：恰好承載一個主張。它的標題不是標籤，而是一句可被引用、帶論證的陳述句——精確到讓指向它的 wikilink，或落在它上面的一次檢索命中，光憑標題就能明確指認這篇筆記在主張什麼，不必回頭讀本文。這就是「主張式標題（title as API）」：其他筆記與未來的檢索都是透過標題與這個主張互動，標題必須獨自扛起這個主張的全部重量。

**為什麼。** 一篇叫「Attention residue」的筆記告訴你一個主題；一篇叫「切換到新任務後，前一個任務的殘留會拖累新任務表現，且殘留強度隨切換前任務的完成度遞減」的筆記告訴你一個主張。只有後者能被其他筆記有意義地引用、同意或反駁。標題若含糊，筆記之間的連結就不再是論證關係，只淪為模糊的主題聯想。

**落在哪些行為。** 本文的任務是把這個主張背後的全部素材——機制、因果鏈、推導、量化數據、邊界條件——按源素材的份量如實承載，不多不少。為求清楚簡化措辭沒問題，但收窄或誇大主張本身不行。原子筆記裡的每一句話都必須能追溯回其源筆記，唯一例外窄到只剩一種情況：一句指向另一篇已歸檔筆記的綜合句，只要它帶著指向該筆記的 inline wikilink，且這個連結關係已經先透過讀那篇筆記全文驗證過，就可以寫入。

## 3. 連結紀律

**理念。** wikilink 是單向、行內的——嵌在本篇筆記行文中確實提及另一篇筆記主張的那句話裡——而且任何地方都不設「Related notes」這種清單。檢索或召回命中本身絕不構成建立連結的理由，它只是候選。連結建立之前，候選的全文必須先讀過，而且本篇筆記的行文必須確實論及那個概念。

**為什麼。** 連結應該代表一種論證關係——本篇依賴、延伸或反駁另一篇——而不是相似度分數。如果光憑召回命中就建連結，卡片盒會被大量「這兩篇在同一次檢索中一起出現」的關係填滿，而不是「這兩個想法確實相關」。這會摧毀順著連結推理論證的價值。

**落在哪些行為。** 暫存層筆記永遠不會是連結對象——它們還不是定稿的主張，沒有穩定的東西可連。兩篇筆記之間的高相似分數，或共用同一個出處，明文都不足以單獨構成建立連結的理由。

## 4. 對抗式審查

**理念。** 每一句寫進筆記的主張——不論是剛草擬的還是剛拆分出來的——都會被一道專責的審查流程檢查，這道流程預設反駁立場：先嘗試推翻每條主張，推翻不了才承認它忠於來源。每條主張最終恰好歸入三類之一：忠實、事實錯誤、存疑。「存疑」不是「大概是錯的」的委婉說法——當審查既找不到背書也找不到矛盾時，存疑就是誠實的結論，而且絕不能被拿來當作降低主張強度、收窄標題或刪除段落的理由。

**為什麼。** 預設信任的審查者，會把看起來合理的錯誤直接放行；把「找不到證據」等同於「錯誤」的審查者，則會把還沒對到正確來源的內容過度刪除。三分類的設計，正是為了不讓這兩種失效模式互相吞噬。

**落在哪些行為。** 審查 agent 本身絕不寫入任何檔案——只能回報。對事實錯誤，它會附上具體的建議修正內容，以及修正所依據的錨定原文；對存疑項目，只回報不附修正建議。真正裁定是否套用建議修正的，是 dispatch 這次審查的指令，逐條評估——審查 agent 自己不會依據自己的發現動手改。而且審查一旦結束，筆記裡不會留下任何審查痕跡：本文與 frontmatter 都不會出現審查相關的標記或紀錄。

## 5. 記憶迴圈

**理念。** 一則慣例（convention）是使用者的習慣——是操作這個 plugin 的人站在 plugin 規則之外的做法，不是 plugin 自己發明的規則。慣例不會被直接寫入；它們只透過恰一個管道進場：提案（proposal），在某個指令察覺到看起來值得記住的使用者習慣訊號時草擬。沒有任何捷徑讓提案跳過佇列直接變成慣例。`/zk:adapt` 就是提案被裁定的地方——逐條、在對話中，由使用者做決定；指令本身絕不代替使用者裁定。被駁回的提案直接刪除；刪除即是封存——不會另外留一份被駁回提案的檔案庫。

**為什麼。** 如果 plugin 可以悄悄採納它自己察覺到的行為模式，使用者就會搞不清楚 plugin 為什麼開始有不同的做法。把每一次採納都導向一個明確、可審視的提案，並要求每一條都經過人的裁定，才能讓 plugin 的行為保持可解釋，也讓使用者對「我喜歡的做事方式」在自己 vault 裡的意義保有掌控權。

**落在哪些行為。** 每個有寫入能力的指令開工前都會掃描既有慣例，並在本次工作中遵守適用者；也會在回報中提示待議提案的存在，但這個提示不具約束力，不會改變或暫停本次執行。

## 6. 工作日誌（devlog）

**理念。** 每篇暫存層筆記都帶著自己的工作日誌（devlog）——一份鏡射其路徑的工作紀錄，一筆記一日誌。如果某次 session 中斷在思考中途，下一次 session 會載入這份日誌，準確看到上次停在哪裡，從那裡接續，而不是從頭重來。日誌是 append-only 的：寫進去的內容絕不會被刪除或改寫，唯一例外是檔案頂端的一份狀態摘要，隨著進度推進可以被重寫。當一篇筆記成功歸入歸檔層後，它的日誌會在那一刻被刪除——刪除即是封存，與被駁回的提案同樣的道理。

**為什麼。** 工作日誌存在的目的，是讓中斷的工作可以被接續，並誠實記錄草擬過程中實際發生的事，同時不讓這些過程細節污染成稿——讀者不需要知道這些。一旦筆記歸檔，讓它走到今天這個主張的推理過程，對讀卡片盒的人已不再重要——重要的只剩定稿的主張，所以過程紀錄不會跟著筆記一起進歸檔層。

**落在哪些行為。** 只有暫存層筆記有工作日誌；歸檔層筆記從來沒有。唯二會讀寫工作日誌的，是產出暫存層筆記的那兩個 lifecycle 指令；permanent 唯一會碰工作日誌的動作，是刪除它剛歸檔那篇筆記所屬的日誌。

## 7. 純 markdown，無腳本

**理念。** plugin 不附帶任何 hooks、不含任何可執行程式碼，也絕不代使用者執行 git 指令。每一項機械紀律——編號、格式、索引維護、檔名規則——全都以文字指示承載，靠模型自律遵循執行，而不是靠程式碼自動強制。

**為什麼。** 一個帶腳本或 hooks 的 plugin，它的行為無法單靠讀檔案內容就看懂——你得追蹤程式碼實際做了什麼。把一切都變成模型讀懂並遵循的指示，意味著整個 plugin 的行為都可以透過讀 markdown 來審視，也讓 plugin 可以隨 vault 移到任何機器上，不必攜帶執行環境。vault 內容的版本控制完全交由使用者自理；plugin 不碰 git，因為 vault 的歷史紀錄是使用者的事，不是 plugin 的事。

**落在哪些行為。** plugin 自身檔案裡出現的程式碼區塊，全部只是用來示範 CLI 呼叫方式或資料格式的範例——絕不是打算被執行的內嵌邏輯。

## 8. plugin 唯讀，vault 自主

**理念。** plugin 自己安裝的檔案在 runtime 是唯讀的——沒有任何指令或 agent 會修改 plugin 自身的檔案；plugin 的異動只透過它自己的開發流程發生，不會由任何使用者的 session 觸發。在 vault 這一側，狀態恰限於四類：config 檔、定義筆記 schema 的模板檔、一個承載慣例、提案與日誌的隱藏目錄，以及筆記本身。

**為什麼。** 把「plugin 是什麼」和「vault 裡有什麼」分開，才能讓 plugin 裝進任意既有 vault 而不打擾原本就在那裡的東西。如果 plugin 會依某個特定 vault 的使用方式改寫自己，它在不同安裝之間的行為就會不可預期地飄移。

**落在哪些行為。** vault 裡既有的筆記，初始化或任何指令都不會搬動或改寫；plugin 不認得的 frontmatter 欄位會原樣保留、不會被剝除，因為它們可能正為其他工具做事（例如供 Obsidian 其他功能讀取的自訂屬性）。每個階段的目錄佈局，全部透過初始化時的訪談由使用者親自決定，不預設任何固定值。config schema 本身保持極簡——一個欄位只在真的有行為會消費它時，才會被加進去。

## 9. 檢索設計

**理念。** 語意檢索（semantic search，可用時）是找出候選筆記的主漏斗，再輔以精確詞的文字檢索，補上語意比對常常漏接的字面 token——識別碼、專有名詞。語意檢索是否可用且被允許使用，是單一一個設定值，也是決定檢索走哪條路的唯一訊號。當這個設定值表示語意檢索關閉時，退回純文字檢索（Grep 降級／Grep fallback）是正當、預期中的路徑——不是錯誤，回報時也不必為此道歉。但當設定值表示語意檢索已啟用時，語意檢索工具本身失敗就必須停下並回報；絕不能悄悄退回文字檢索草草了事，因為一個本該可用卻失敗的工具，是值得被看見的問題，不是該被藏起來的問題。

**為什麼。** 讓這個設定值成為唯一的分流訊號，能讓檢索行為保持可預期——只要看這一個地方，就能知道這次檢索為什麼走了這條路。兩條路徑底下共通的讀全文鐵律（read-the-full-text rule：任何命中都只是候選，不是證據；在真正讀過候選全文之前，不能引用或建立連結）存在的理由，是因為相似度分數與命中次數描述的是檢索引擎怎麼排序，不是它是否真的講了你需要的那件事。

**落在哪些行為。** 索引維護恰發生在兩個時點：lifecycle 指令開始處理暫存層筆記時的一次冪等 reindex，以及 permanent 收尾時的一次增量 reindex。沒有其他指令會碰索引。當語意檢索整個關閉時，就沒有索引需要維護，這兩個維護點都會被跳過。

## 10. Agent 邊界

**理念。** 三個 subagent 各自只做一件事，且各自圍著一條不可逾越的邊界。research agent 讀來源全文並回報結果——唯讀、無寫入權限——如果它實際上拿不到來源的全文，它會直接中止，而不是拿摘要、書評或自己訓練知識裡的東西頂替；拿二手資料代替真正的來源，是它唯一絕不退讓的紅線。atomizer 從頭到尾全自主運作——每個判斷（在哪裡切分一篇筆記、用哪個 topic tag、什麼時候該新增一個 topic 分區、如何化解命名衝突）都自己拿主意，絕不中途停下來提問。對抗式審查 agent 唯讀、只回報——它拿到的發現如何被處理，見上面第 4 節的說明。

**為什麼。** 這三條邊界各自保護不同的東西。research 的邊界保護卡片盒不被二手轉述汙染——轉述的轉述，會慢慢偏離來源實際說的話。atomizer 的全自主性，是因為拆分本身是個量大、機械性足夠高的決策空間，若每次切分或每次選 tag 都要停下來問，整條管線根本跑不動；而防範這種全自主性出錯的防線，正是緊接其後的對抗式審查。審查的唯讀邊界，則是要把「真正動手改筆記」的裁定權留在 dispatch 這次審查的指令手上，而不是讓一個被設計成預設懷疑一切的 agent，同時也成為決定該怎麼處理自己發現的那個人。
